文件系统挑战性任务 — 实现报告

任务一

Thinking 1.1

请思考并回答，在真实的操作系统中，如果使用内存中的地址作为文件控制块的字段，会出现哪些问题？为什么我们目前的操作系统不会出现这些问题？

在真实的操作系统中，如果使用内存地址作为文件控制块字段，会出现以下的问题：

  1. 操作系统中不同进程拥有独立的虚拟地址空间，若使用内存地址作为文件控制块的字段，该地址只在当前进程的虚拟地址空间中有意义，若另一个进程访问该地址，就可能会出现错误。
  2. 进程关闭文件、退出或内存被释放时，该文件控制块中保留的旧地址会被回收并分配给其他数据，引发冲突。
  3. 内存地址在系统重启后就会失效，而文件控制块会被保存到磁盘，存活的时间更长，因此文件控制块应该使用磁盘块编号和块内偏移这些字段。

我们目前的操作系统不会出现这些问题的原因：

  1. 我们目前的系统中文件系统运行在单一进程地址空间中，不会出现多进程地址空间冲突。
  2. 在我们目前的系统中磁盘块到内存地址的映射是一对一固定的（DISKMAP + blockno * BLOCK_SIZE），磁盘块会被加载到固定的地址，因此映射的地址不会变化，不会出现这些问题。
  3. 我们目前的系统中f_dir是临时的，每次文件查找过程都会重新设置f_dir，而不会存入磁盘持久使用。

Challenge 1.1

请在 user/include/fs.h 文件中找到 struct File 结构体的定义，并将其中的 f_dir 字段修改为 f_dir_block 和 f_dir_offset 两个字段，分别记录 当前文件所在的目录 的文件控制块 所在的磁盘块编号，以及当前文件所在的目录 的文件控制块 在磁盘块中的偏移。注意维护 f_pad 字段的长度，保证 struct File 结构体大小依然为 256 字节。

  • 在user/include/fs.h中找到struct File结构体，删除其中的struct File *f_dir，改为uint32_t f_dir_block和uint32_t f_dir_offset。
  • 由于减少了一个指针，增加了两个uint32_t，将char f_pad[FILE_STRUCT_SIZE - MAXNAMELEN - (3 + NDIRECT) * 4 - sizeof(void *)]改为char f_pad[FILE_STRUCT_SIZE - MAXNAMELEN - (3 + NDIRECT + 2) * 4]保持struct File结构体大小为256字节。
  • 由于修改了struct File结构体，多增加了两个uint32_t字段，需要在tools/fsformat.c中修改reverse_block函数，模仿其他uint32_t字段的字节序反转方式，对新增加的两个uint32_t字段进行字节序反转。

任务四

Thinking 4.1

Thinking 4.1 请自行设计一种检查地址是否已分配，并实现地址分配的方案。需要满足以下三个要求：一是可供分配的地址范围为 [0x10000000, 0x50000000) ；二是保证已分配的地址能够正确被回收；三是保证较低的地址优先被分配。在设计好分配方案后，分析该方案占用的时间和空间，并据此简述为什么选取该方案。提示：你可以回顾本学期实验课程中遇到的所有分配方案，例如页控制块和进程控制块的分配、asid 的分配、fileid 的分配、fdnum 的分配等。

  • 我选择采用位图法方案。使用一个字节数组cache_bitmap[]来记录缓存页的分配情况，数组大小为(0x50000000 - 0x10000000) / 4k = 262144，每 bit 对应一个缓存页。bit=1 表示已分配，bit=0 表示空闲。使用一个数组cache_addr_map[]来记录磁盘块号到虚拟地址的映射，索引为磁盘块号，值为缓存虚拟地址，0 表示未缓存。
  • 占用时间：分配：O(N)；回收：O(1)；检查是否空闲： O(1)。
  • 占用空间：cache_bitmap：262144 bits = 32768 B = 32 KB；cache_addr_map：262144 × 4 B = 1 MB
  • 选取该方案的原因：位图法简单易实现，不容易出错。并且在回收和检查是否空闲时，时间复杂度为 O(1)，性能较好。位图法在每次分配时都重新从低地址向高扫描，所以可以优先分配较低地址且对于回收的低地址后续分配也会考虑到，符合题目需求。

Thinking 4.2

Thinking 4.2 请自行设计一种数据结构，用于存储磁盘块编号到缓存地址的映射，使得时间复杂度最小。注意存储并维护磁盘块编号不对应任何缓存地址的状态（即磁盘块未被缓存的状态）。

  • 如第一个思考题中的方案，我采用一个哈希表来存储磁盘块编号到缓存地址的映射，哈希表的键为磁盘块编号，值为缓存虚拟地址，值为 0 表示未缓存。此时查找，建立映射和删除映射的时间复杂度都为O(1)。

Challenge 4.1

新增函数：

cache_init：初始化缓存位图和映射表。syscall_mem_alloc一次只分配一页，而cache_addr_map需要 256 页，cache_bitmap需要 8 页，所以循环逐页分配。

由于映射方式变了，disk_addr和ptr_to_blockno函数不能再使用之前的公式计算，需要修改：
那么此时disk_addr就有了返回NULL的可能性，因此所有调用了disk_addr的地方都需要修改，增加对返回值va == NULL的检查。block_is_mapped、block_is_dirty、dirty_block、write_block这四个函数中需要对disk_addr返回值va == NULL的情况增加特殊处理。
并且由于映射方式的更改，read_block、map_block、unmap_block这三个函数需要修改。
  • read_block改为：如果cache_addr_map[blockno] != 0且该va 确实已映射，直接isnew = 0。否则先调用 alloc_cache_page()获取新地址，再写入 cache_addr_map[blockno]，通过syscall_mem_alloc分配物理页，最后ide_read 读磁盘，置isnew = 1。
  • map_block(blockno)改为：不再用 disk_addr(blockno) 取固定地址，而是用alloc_cache_page()获取新地址并记录映射。
  • unmap_block(blockno)新增两步：cache_addr_map[blockno] = 0清除映射，表示该块不再被缓存，并free_cache_page(va)回收缓存页，让其后续可以被重新分配。
采用动态分配后，原来的基于假设连续分配的磁盘位图失效了

可以设置一个本地连续副本local_bitmap来解决这个问题。在read_bitmap()中，分配local_bitmap全部所需页面，在逐个读入位图块，把内容拷贝到local_bitmap的对应位置，最后把全局bitmap指针指向local_bitmap。

然后将所有位图操作block_is_free、free_block、alloc_block_num都改为操作local_bitmap。若需要写回磁盘，则在写回时需要先根据修改的 blockno 计算它属于哪个位图块，再将该位图块在 local_bitmap 中的对应部分 memcpy 到该位图块当前缓存地址，最后write_block写回磁盘。
