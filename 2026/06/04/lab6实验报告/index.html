Thinking6.1如果不关闭自己不会用到的管道端会怎么样？

  • 如果不关闭自己不会用到的管道端，会因内核维持的管道引用计数无法降为零而导致进程在读取时永远阻塞，或者因写入无读端的管道而收到相应信号导致程序崩溃，同时还会造成文件描述符资源泄漏，最终使系统出现死锁、资源耗尽或意外终止等严重问题。

3.

Thinking 6.3 MOS 中的管道缓冲区大小 PIPE_SIZE 过小有什么影响？缓冲区大小是怎么影响吞吐和切换效率的？

  • 管道缓冲区过小，会严重影响进程间的数据吞吐量和切换效率。由于内核需要维护读写指针，当生产者写入数据使 p_wpos - p_rpos >= PIPE_SIZE 时，就会被强制挂起，等待消费者读取。如果缓冲区太小，这种“写满”会频繁发生，导致生产者和消费者之间极高频次的上下文切换，因为它们需要不断在内核态和用户态之间来回切换以处理阻塞与唤醒。这不仅浪费了CPU资源，也使得系统难以在高数据量下保持稳定，导致吞吐量大幅下降。

4.

Thinking 6.4 上面这个恒等式在所有时刻都成立吗？请给出你的分析过程(若不成立，会在哪些时刻不成立？)，如果不成立，是否会造成误判？

  • 不是在所有时刻都成立。在管道创建过程中，系统先分配 pipe 结构体，此时 pageref(pipe) 可能为 0 或 1（取决于初始化策略），但尚未创建 rfd 和 wfd，故等式左边为 0，右边可能为 0 或非零，不一定相等。在关闭管道一端的过程中，调用 close(rfd) 时，系统先减少 rfd 的引用计数（或标记为无效），然后才去释放对 pipe 的引用。在两者操作之间（例如正在执行文件描述符表的清理，但尚未调用 pipe_close 更新 pipe 的引用计数），就会出现左边已减少而右边尚未减少的情况，导致暂时不相等。在多进程/多线程并发时，如果多个进程通过 fork 或 dup 共享同一个管道的读端或写端，那么恒等式的左边应该包含所有读端和写端的 pageref 之和，而不仅仅是单一 rfd 和 wfd。此时直接用两个描述符的引用计数来和 pageref(pipe) 比较自然不成立。而且引用计数的更新不是原子操作，在无锁保护的情况下，对文件描述符和管道结构体的引用计数增减可能被线程调度打断，导致某个瞬间观察到的不一致。可能会造成误判，如果系统依赖该恒等式进行资源回收（例如判断管道是否可以被释放），则可能在创建或关闭的中间状态，左边小于右边，系统可能误以为仍有引用（右边较大）而不敢释放，造成管道泄漏。或者在另一边，左边大于右边（如关闭过程中左边已减但右边未减），系统可能误认为管道引用计数已为 0，提前释放 pipe 结构体，导致后续访问已释放内存，引发内核崩溃或数据损坏。

Thinking 6.5 上面这种不同步修改 pp_ref 而导致的进程竞争问题在 user/lib/fd.c 中的dup 函数中也存在。请结合代码模仿上述情景，分析一下我们的 dup函数中为什么会出现预想之外的情况？

  • 在dup中，先对文件描述符进行映射，后对文件内容进行映射。如果在这两个系统调用中发生进程的中断，根据文件描述符的pp_ref将判断映射已经完成，而实际上文件内容并未被映射。

Thinking 6.6 阅读上述材料并思考：为什么在我们的MOS中，系统调用一定是原子操作呢？如果你觉得不是所有的系统调用都是原子操作，请给出反例。希望能结合相关代码进行分析说明。

  • 我们的MOS是单核的，只有一个进程一个线程。在进行系统调用前关闭了中断，不会出现在syscall中再次出现系统调用的情况，因此可以确定在我们的MOS系统中系统调用一定是原子操作。

Thinking 6.10 在shell中执行的命令分为内置命令和外部命令。在执行内置命令时shell不需要fork一个子shell，如Linux系统中的cd命令。在执行外部命令时shell需要fork一个子shell，然后子shell去执行这条命令。据此判断，在MOS中我们用到的shell命令是内置命令还是外部命令？请思考为什么Linux的cd命令是内部命令而不是外部命令？

  • 我们在MOS中用到的shell命令时外部命令。因为其每次运行都要使用child = syscall_exofork();创建新进程来执行
  • cd 命令的作用是改变当前进程的工作目录。如果其是外部命令的话，执行时就会创建新进程，此时就无法改变父进程的环境，当前目录不会改变，无法完成其功能

难点分析

lab6主要管道和shell方面的知识，在完成lab6章节之后，我们的操作系统看起来也是有模有样基本实现成功了。lab6有非常多的知识 基于lab5，这一章的内容需要我们对lab5有较高的掌握度。

管道的核心难点在于pageref的管理，这也是MOS首次出现关于调整先后执行顺序的问题。问题的核心原因在于判断读端或写端是否关闭时，使用了pageref的方法，而这个条件在某些中间状态下并不充分。

SHELL需要我们熟悉流程，关键是parsecmd和spawn两个函数。从SHELL中读取token并解析命令，然后调用spawn对ELF文件进行打开加载运行等等操作。
